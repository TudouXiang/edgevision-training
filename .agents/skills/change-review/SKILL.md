# 变更审查（只读）

## 触发条件

用户要求提交前审核本项目的 diff、未提交改动、候选提交或某项交付是否满足任务单。

## 输入

需求和任务 ID、明确的基线/目标分支、`git status` / 暂存/未暂存/未跟踪 diff、`docs/` 契约与验收、提交者给出的原始测试证据。无 upstream 时不得臆造未推送提交范围。

## 步骤

1. 以需求追踪所有修改；判断有无更小、符合现有架构的实现与复用机会。
2. 检查普通用户/管理员权限、文件路径和 ZIP 解压、SQLite 并发、Worker 子进程回收、进度/产物真实性。
3. 区分已实际运行的测试与自报结果；定位到文件与行，优先报告可复现缺陷和跨模块回归。
4. 如范围包含未推送提交，确认 upstream 与提交集合；不默认 origin/main，不自动 fetch、stash 或修复。性能意见须有实际调用/资源证据或明确为待测假设。

## 输出

按严重度排列的发现（路径/行、复现条件、影响、最小修复），验收覆盖和 accept / changes_requested / insufficient_evidence 结论；无发现也列出范围和证据缺口。使用 [评审模板](references/output-template.md)。

## 停止条件

没有需求或基线、diff 不完整、无法分清既有未提交改动归属、只能推测而不能定位问题。注明证据不足，不直接修改代码或伪称验收。[行为用例](references/eval-cases.md) 不是实际执行的审查。
