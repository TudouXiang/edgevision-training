# 架构规范

## 触发条件

任务涉及范围、公共接口、数据库、文件规则、任务状态或技术栈的新增/修改；或发现现实资产与已冻结 ADR 冲突。

## 输入

任务/变更请求、`AGENTS.md`、`docs/status.md`、`docs/scope.md`、`docs/architecture.md`、`docs/contracts.md`、相关 ADR、Git 差异、实际源码与运行证据；先确认目标仓库。

## 步骤

1. 写明原基线、观察到的现实、冲突或风险；分别判断是否改产品范围、公共契约、迁移或部署拓扑。
2. 比较至少一个更小的兼容调整；说明数据迁移、旧客户端影响、测试和回退。重大变更先向用户说明影响和最小方案。
3. 只更新受影响的 ADR、契约、状态与任务；保持数据库、后端类型、前端 TS 类型同步。
4. 区分设计、源码、执行和假设。涉及学校硬性要求、产品承诺、费用、硬件或未授权资源，只整理受影响部分供用户裁决；不自行变更范围。外部 API/版本兼容性查对应版本官方资料。

## 输出

一份可审阅的决策记录：决定、理由、未选方案、兼容性/迁移方案、受影响文件、所需验证与未验证项。使用 [决策模板](references/output-template.md)。

## 停止条件

目标仓库/原始基线不明、学校要求与范围冲突、用户授权不足、无法定义数据迁移或验证方法；仅停止受影响的工作并记录阻塞，不擅自扩大范围。[行为用例](references/eval-cases.md) 不是实际验收。
